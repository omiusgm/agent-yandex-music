# Работа со списками и метаданными

Команды выполняются из корня установленного проекта. Вход в аккаунт описан в [README](../README.md). Файлы `outputs/` и `exports/` — приватные результаты работы, они не публикуются вместе с кодом.

## 1. Полный снимок

```bash
.venv/bin/python scripts/account_export.py \
  --token-file "$HOME/.yandex-music-mcp/token" \
  --output outputs/current-snapshot
```

В результате сохраняются `library.json`, читаемый `playlists.txt`, `coverage.json`, исходные JSON и манифест с хешами. Состав берётся через `rich-tracks=false`, чтобы не потерять ID недоступных треков при получении подробных метаданных.

Проверьте в `coverage.json` полноту области выгрузки, ошибки, расхождения количества треков и изменения ревизий. При наличии актуальных счётчиков интерфейса их можно передать флагами `--expected-owned` и `--expected-liked`. Учитывайте, что интерфейс может включать системный «Мне нравится» в общий счётчик.

`--resume` подходит для продолжения прерванной выгрузки. Для нового снимка после изменений используйте новую папку или запускайте без этого флага.

Без авторизации доступна только публичная часть:

```bash
.venv/bin/python scripts/public_export.py \
  --login YOUR_PUBLIC_LOGIN --output outputs/public-snapshot
```

Здесь `YOUR_PUBLIC_LOGIN` нужно заменить своим публичным логином. Такой снимок не доказывает полноту аккаунта и не служит основанием для удаления исходных плейлистов.

## 2. Анализ без сети

```bash
.venv/bin/python scripts/analyze_library.py \
  --input outputs/current-snapshot/library.json \
  --output outputs/analysis --collection owned
```

Анализатор не обращается к аккаунту. Он сравнивает точные пары `track_id:album_id`, показывает пересечения и помогает выбрать группы. Совпадение названия песни не делает разные версии одним треком. Отчёт — материал для решения владельца, а не готовое разрешение на изменения.

## 3. Явный черновик групп

Создайте `outputs/analysis/grouping-draft.json` с таким устройством:

```json
{
  "groups": [
    {
      "group_id": "g01",
      "title": "Название объединённого плейлиста",
      "rationale": "Почему эти подборки стоит объединить",
      "source_kinds": ["1001", "1002"]
    },
    {
      "group_id": "g02",
      "title": "Оставить отдельно",
      "rationale": "Отдельное назначение",
      "source_kinds": ["1003"]
    }
  ]
}
```

Числа здесь вымышленные: замените их `kind` из **своего** снимка. Каждый обычный собственный плейлист должен входить ровно в одну группу. Для сохранения отдельного списка создайте группу из одного элемента. Системный `kind=3` и чужие понравившиеся плейлисты в группы не включаются.

```bash
.venv/bin/python scripts/compile_merge_plan.py \
  --library outputs/current-snapshot/library.json \
  --groups outputs/analysis/grouping-draft.json \
  --output outputs/analysis
```

Проверьте `merge-plan.txt` и `merge-plan.json`. Компилятор выбирает существующий плейлист-основу, вычисляет добавления и сохраняет происхождение треков. В плане сохраняются существующие повторы основы, а одинаковые пары трек/альбом из других источников не добавляются повторно. Все исходные вхождения остаются в снимке.

## 4. Проверка и перенос

Команда без `--apply` проверяет актуальные источники, но не меняет аккаунт:

```bash
.venv/bin/python scripts/apply_merge_plan.py \
  --plan outputs/analysis/merge-plan.json \
  --snapshot outputs/current-snapshot/library.json \
  --token-file "$HOME/.yandex-music-mcp/token" \
  --run-dir outputs/merge-execution
```

После согласования конкретного плана с владельцем:

```bash
.venv/bin/python scripts/apply_merge_plan.py \
  --plan outputs/analysis/merge-plan.json \
  --snapshot outputs/current-snapshot/library.json \
  --token-file "$HOME/.yandex-music-mcp/token" \
  --run-dir outputs/merge-execution \
  --apply --phases private,add,rename
```

Эта фаза может сделать основу приватной, добавить недостающие треки и переименовать её. Исходные списки ещё сохраняются. Проверяйте `last-report.json` и журнал: отдельная группа может остановиться. При неопределённом результате запроса сначала перечитайте фактическое состояние; повторная отправка вслепую может продублировать изменение.

## 5. Удаление источников — отдельная фаза

Только после проверки состава назначений и разрешения владельца на удаление названных источников:

```bash
.venv/bin/python scripts/apply_merge_plan.py \
  --plan outputs/analysis/merge-plan.json \
  --snapshot outputs/current-snapshot/library.json \
  --token-file "$HOME/.yandex-music-mcp/token" \
  --run-dir outputs/merge-execution \
  --apply --phases retire --retire-user-approved
```

Сохраняйте тот же план, снимок и журнал между фазами. Для нового плана используйте отдельный каталог выполнения. `--groups g01` ограничивает запуск согласованной группой. Недоступный трек может не переноситься: пока фактический состав назначения не подтверждён, источник остаётся.

После завершения сделайте свежую выгрузку в отдельную папку и сравните результат с планом. Не перезаписывайте единственный снимок до объединения.

## Обложки и порядок

Скрипты не создают недостающие изображения или манифесты автоматически. В публичной поставке нет персональных обложек и заранее выбранного порядка.

Для `apply_playlist_covers.py` нужен JSON вида `{"covers": [{"playlist_id": "UID:KIND", "title": "Название", "image_path": "cover.png"}]}`. Путь изображения может быть абсолютным или относительным к манифесту. Используются PNG/JPEG до 20 МБ со сторонами меньше 2500 пикселей. Сначала откройте изображение и выполните запуск без `--apply`; изменение выполняется только с этим флагом. Старые собственные обложки и метаданные сохраняются в каталоге выполнения. Автоматический возврат к исходной мозаике не гарантируется.

Приоритет можно рассчитать офлайн по датам сохранившихся добавлений:

```bash
.venv/bin/python scripts/rank_playlists.py \
  --snapshot outputs/current-snapshot/library.json \
  --days 90 --timezone UTC \
  --output outputs/analysis/playlist-priority.json

.venv/bin/python scripts/order_playlists.py \
  --priority outputs/analysis/playlist-priority.json \
  --token-file "$HOME/.yandex-music-mcp/token"
```

Первая команда создаёт файл, вторая показывает предлагаемый порядок без изменений. Выберите подходящий часовой пояс через `--timezone`. Расчёт относится к дате снимка и сохранившимся записям; он не восстанавливает удалённые добавления и не измеряет прослушивания.

Для переноса исторического приоритета на результаты объединения `rank_playlists.py` принимает `--plan` вместе с соответствующим исходным снимком; хеш снимка должен совпасть с планом. Перед изменением порядка нужны актуальные данные и согласованный список. `order_playlists.py --apply` меняет порядок с повторным чтением. Подтверждённый серверный порядок не гарантирует, что конкретная версия мобильного диалога уже обновила свой кэш.

## Передача личного снимка агенту

После полной выгрузки и анализа:

```bash
.venv/bin/python scripts/build_handoff.py \
  --input outputs/current-snapshot/library.json \
  --analysis-dir outputs/analysis \
  --output outputs/handoff
```

Без `--analysis-dir` архив содержит только выбранный снимок с соседними `playlists.txt` и `coverage.json`, исходники и документацию. Дополнительные отчёты берутся только из указанного каталога. Для намеренной передачи исторической библиотеки добавьте `--history путь/к/выбранной-библиотеке.json`, для сведений об обложках — `--covers путь/к/выбранным-обложкам.json`; изображения этим параметром не добавляются. Старые `outputs/analysis`, `outputs/current-analysis`, история и обложки автоматически не подбираются. Убедитесь, что выбранные отчёты относятся к нужному аккаунту и снимку.

Получившийся архив содержит вашу медиатеку. Передавайте его только выбранному агенту или получателю. Он предназначен для анализа и передачи контекста; для установки актуальных инструментов используйте этот Git-репозиторий. Архив не должен содержать токен, `.env`, профиль браузера или виртуальное окружение.
